# 易居 GPT 浏览器证据归档桥｜上线与验收

## 目标
保留用户明确要求的 **ChatGPT 原生运营窗口 + 现有易居 Node 服务** 架构。不额外部署 Agent 服务。此变更在原管理员后台增加一种不需要单独的机器 API 密钥的临时连接方式，方便本对话中的 TinyFish 使用保存的浏览器会话完成证据入库。

## 新功能
- POST `/api/admin/city-agent/evidence`：现有 JWT + admin 权限控制。复用 `/api/agent/city-data/submissions` 的同一个格式验证、证据表、idempotency 和来源字段。
- **严格 evidence-only**：包含 `proposal` 的请求直接返回 400；入库不会调用字段变更、自动审核、发布、回滚。
- `/admin.html` 城市数据管理新增「GPT 证据归档入口」：必须先选择具体城市 ID（注意综合榜「张掖」1490、躺平榜「张掖市」951 的区别），填写 HTTPS 来源、实际读取状态、来源片段、统计周期、指标数值单位、稳定 external_id；提交成功返回证据 ID，重复返回 replayed。
- 现有机器密钥的 Agent API 不变；自动更新每日十条限制不变。

## 一次上线与回归（Codex）
1. 以本 PR 为候选，先执行 `npm run test:city-data`、`npm run test:city-data:sqlite`，重点检查 admin JWT 401/403、重复提交 200 replayed、同 ID 不同内容 409、带 proposal 的管理员证据路由 400、城市 ID 1490/951 不混淆。
2. 核对生产备份、恢复与可回滚部署条件，保留原服务配置；仅更新现有 Node 服务和 admin JS 静态资源。不得创建额外 Agent 进程。
3. 先执行 **只读** 生产复验，再经授权做一条真实来源的 evidence-only 归档（推荐张掖市 951，政府公报 2025 年医疗卫生机构数据），不可将机构数量当成评分。使用新 external_id，明确记录证据 ID、城市 ID 和回读结果。
4. 使用已保存的 TinyFish 登录浏览器打开「城市数据管理」，选择 951，填写来源，提交一次，刷新「GPT 采集证据收件箱」筛选 951；确认历史 1490 的两条证据未被合并或改写。重复同 external_id 同内容应幂等。
5. 检查原有公开城市页面、榜单、小程序共用 API、管理员审批和回滚无回归。
6. 将生产 SHA、实际记录证据、CI 和浏览器结果、P0/P1 写到 PR 的验收回执。

## 关于无人值守
此浏览器方案能证明 GPT 在**本对话即时调用 TinyFish** 的情况下完成表单提交流程。**它不保证 ChatGPT 定时任务可以自动调用 TinyFish 插件或保证登录长期有效**。这两个能力必须再由一次实际的定时任务验收确认。避免把“浏览器登录复用”和“长期无人值守”混为一谈。

此外，保存的管理员浏览器配置具有管理权限，自动化提示必须限制为证据入库；长期无人值守最好采用独立低权限的 GPT 服务凭据/角色。不得将管理员 JWT 或原始 Agent API token 输出到聊天、GitHub 或日志。
